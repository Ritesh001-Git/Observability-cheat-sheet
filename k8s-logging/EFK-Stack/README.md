# EFK Stack (Elasticsearch, Fluent Bit, Kibana)

The **EFK Stack** is used for collecting, processing, storing,
searching, and visualizing logs from applications running in Kubernetes.

The stack consists of:

-   **Elasticsearch** -- Stores and indexes logs.
-   **Fluent Bit** -- Lightweight log collector and processor that
    collects, filters, enriches, and forwards logs.
-   **Kibana** -- Provides a web interface for searching, analyzing, and
    visualizing logs.

# Components

### Elasticsearch

Elasticsearch is a distributed search and analytics engine that stores
and indexes logs.

It receives processed logs from Fluent Bit and makes them searchable.
Elasticsearch allows logs to be retrieved and analyzed efficiently based
on fields such as:

-   Timestamp
-   Namespace
-   Pod name
-   Container name
-   Log level
-   Message
-   Kubernetes labels

### Fluent Bit

Fluent Bit is a lightweight and high-performance log collector and
processor.

In Kubernetes, Fluent Bit typically runs as a **DaemonSet**, which means
a Fluent Bit Pod runs on every Kubernetes node.

Fluent Bit:

-   Reads container log files from Kubernetes nodes.
-   Collects logs generated by application containers.
-   Parses and filters log records.
-   Adds Kubernetes metadata.
-   Can transform and enrich log records.
-   Forwards processed logs to Elasticsearch.

Typical Kubernetes container logs are available under:

``` text
/var/log/containers/
```

Fluent Bit performs both the **collection and processing** stages of the
EFK pipeline.

### Kibana

Kibana is a visualization and monitoring interface that connects to
Elasticsearch.

It provides a web interface where users can:

-   Search logs
-   Filter logs
-   View application errors
-   Analyze log patterns
-   Create visualizations
-   Build dashboards
-   Monitor application behavior

Kibana does not normally store the logs itself. It queries Elasticsearch
and displays the data stored there.

# How Everything Works Together

## 1. Kubernetes Pods

Applications run inside Kubernetes Pods.

As applications execute, they generate logs such as:

``` text
INFO Application started
INFO User request received
WARN Database response is slow
ERROR Database connection failed
```

These container logs are written to log files on the Kubernetes node.

A common location is:

``` text
/var/log/containers/
```

## 2. Fluent Bit Collects Logs

Fluent Bit runs as a **DaemonSet** in the Kubernetes cluster.

Because it is a DaemonSet, Kubernetes schedules a Fluent Bit instance on
each node.

Fluent Bit reads the container log files from the node and collects the
logs.

It can also add Kubernetes metadata such as:

-   Namespace
-   Pod name
-   Container name
-   Node name
-   Container ID
-   Kubernetes labels

Example:

``` text
Application Log
      +
Kubernetes Metadata
      ↓
Fluent Bit Event
```

## 3. Fluent Bit Processes the Logs

Unlike a simple log shipper, Fluent Bit can also process log records
before sending them to Elasticsearch.

A typical Fluent Bit pipeline consists of:

``` text
Input → Parser / Filter → Output
```

For example:

``` text
Container Log
     ↓
Fluent Bit Input
     ↓
Parse Log
     ↓
Add Kubernetes Metadata
     ↓
Filter / Transform
     ↓
Send to Elasticsearch
```

Fluent Bit can be configured to:

-   Parse log formats.
-   Filter unwanted records.
-   Modify fields.
-   Add metadata.
-   Enrich log events.
-   Route logs to outputs.

For example:

``` text
Raw Log:

2026-09-20 ERROR Database connection failed
```

can be transformed into structured fields such as:

``` text
timestamp: 2026-09-20
level: ERROR
message: Database connection failed
```

## 4. Elasticsearch Stores the Logs

After Fluent Bit processes the logs, it sends them to Elasticsearch.

Elasticsearch:

-   Stores the logs.
-   Indexes the logs.
-   Makes logs searchable.
-   Allows filtering based on individual fields.
-   Supports large-scale log analysis.

For example, you can search for:

``` text
level: ERROR
```

or:

``` text
namespace: production
```

or:

``` text
pod.name: backend
```

## 5. Kibana Visualizes the Logs

Kibana connects to Elasticsearch.

Kibana queries Elasticsearch and displays the results through its web
interface.

You can use Kibana to:

-   Search logs
-   Filter logs
-   Find application errors
-   Analyze log frequency
-   Create visualizations
-   Create dashboards
-   Monitor application activity

For example, a Kibana dashboard could display:

``` text
Total Logs
     │
     ├── INFO
     ├── WARN
     └── ERROR
```

# EFK vs ELK

Both EFK and ELK are centralized logging architectures.

### EFK

``` text
Kubernetes
    │
    ▼
Fluent Bit
    │
    │ Collect + Process
    ▼
Elasticsearch
    │
    ▼
Kibana
```

### ELK + Filebeat

``` text
Kubernetes
    │
    ▼
Filebeat
    │
    ▼
Logstash
    │
    │ Process + Transform
    ▼
Elasticsearch
    │
    ▼
Kibana
```

The main architectural difference is the log collection and processing
layer.

In the EFK setup, **Fluent Bit handles both log collection and
processing**.

In the ELK setup, **Filebeat commonly handles log collection while
Logstash handles additional processing and transformation**.

# EFK Stack in Kubernetes

For a local Kubernetes environment such as **Kind**, the architecture
can be deployed as:

``` text
Kind Cluster
│
├── Application Pods
│       │
│       └── Container Logs
│
├── Fluent Bit
│       │
│       └── DaemonSet
│
├── Elasticsearch
│       │
│       └── Deployment / StatefulSet
│
└── Kibana
        │
        └── Deployment
```

This allows the complete EFK logging pipeline to be tested locally
without requiring managed Kubernetes logging services.

# Example Logging Flow

Suppose an application running inside a Kubernetes Pod generates:

``` text
ERROR: Payment service unavailable
```

The flow would be:

``` text
Application Pod
      │
      ▼
Container Log
      │
      ▼
Fluent Bit
      │
      │ Adds Kubernetes Metadata
      │ Processes Log
      ▼
Elasticsearch
      │
      │ Stores + Indexes
      ▼
Kibana
      │
      ▼
Developer Searches:
"Payment service unavailable"
```

Kibana can then be used to identify:

-   Which Pod generated the error.
-   Which container generated the error.
-   Which namespace contains the Pod.
-   When the error occurred.
-   How frequently the error occurred.
-   Whether similar errors occurred elsewhere.
